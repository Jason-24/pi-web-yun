# Settings panels: plugins, skills and shared blocks

## General appearance
- Settings use one persistent sliding category underline and the shared `useSurfaceTransition` 160ms opacity entrance on desktop section/detail changes; category weights stay constant so selecting a tab does not shift its neighbours. The underline measures tab positions on selection, localization and resize. Models, Skills, Plugins, Agents and MCP pass only their selection/mode as `ConfigDetail.motionKey`, so typing, polling and saving do not replay it. Shared controls use short hover/focus transitions and a 1px press offset. Phone navigation keeps its own level animation. Reduced motion disables these transitions and press offsets; content updates, focus, drafts and scroll remain immediate.
- Breeze (`breeze`, 清风/清風) is a built-in light theme with a white reading surface, pale blue user bubbles and soft blue/mint washes on the workspace backdrop and sidebar. Broad, translucent radial gradients overlap a near-white base across the sidebar's full height; keep the color difference subtle rather than a saturated top-to-bottom ramp. Its optional `--workspace-*` tokens customize only the outer shell/sidebar, radius and shadow; other palettes keep the existing fallbacks, and mobile keeps its edge-to-edge frame. The full-width gradient swatch follows System, preserving the five-column light/dark rows. It uses the existing `pi-theme` persistence and first-paint initialization. `e2e/breeze-theme.mjs` checks desktop and 390/320px phones, palette selection/persistence, AA text contrast, draft preservation and switching back to other themes, with isolated APIs and screenshots under `test-results/breeze-theme/`.
- Settings category tabs, including the selected category, and the close button keep a distinct keyboard focus outline in addition to their hover and selected states.
- Desktop category tabs size to their localized labels with a minimum touchable width instead of a fixed 96px, so more categories fit beside an open file panel; the strip still scrolls when needed and the phone picker remains unchanged.
- The default interface font stack explicitly includes PingFang SC, Microsoft YaHei and Noto Sans CJK SC before generic sans-serif, so Chinese follows the same sans-serif style as the interface. User font overrides continue to take priority, and no new font downloads or saved preference changes are involved.
- `components/FontSettings.tsx` offers separate interface/chat and monospace (code, tool output, terminal) font-name lists in the Fonts & layout section after Appearance, together with chat font size (which also sets the terminal's, hence its "Chat & terminal font size" label; client-platform.md) and content width; the Chat section keeps only behavior switches. Every row there has one shape: a header line (label, value, reset button in a fixed 28px column) over a full-width slider, so values and resets line up. A font row puts its name field between label and value, and its slider is the weight (100–600, step 100; `aria-valuetext` adds the weight's name). Both font rows share one grid (`subgrid`), so their name fields start at the same x whatever the labels' widths in each locale. The name field is drawn in the font it names, which is the preview; keep one short section description, no separate preview lines or per-control paragraphs. `hooks/useFontPreferences.ts` stores them only in the browser (`pi-ui-font-family`, `pi-mono-font-family`), applies changes immediately through `--font-ui` / `--font-mono`, and syncs other tabs. AppShell keeps the hook mounted so restoring a font never requires opening Settings or a chat. Empty input removes the override; the original stacks stay in `app/globals.css` as `--font-ui-default` / `--font-mono-default`.
- Font names refer to fonts on the **browser's device**, not the server; no enumeration, upload or remote download. `lib/font-preferences.ts` treats commas as separators, accepts optional enclosing quotes, quotes non-generic names as data, and always appends the default stack. Never interpolate font input into a stylesheet or accept it as executable CSS. Keep raw input whitespace while typing so multi-word names remain editable.
- Each font has a separate base weight (100–600 in steps of 100, default Regular/400; it stops at 600 because headings and labels use 600 and bold text, highlighted bold and the terminal's bold use 700, so a heavier base would outweigh them), stored as `pi-ui-font-weight` / `pi-mono-font-weight` and applied through `--font-ui-weight` / `--font-mono-weight`. Missing/invalid stored weights use 400; saving 400 removes the override. Each reset clears that font's name **and** weight in one update, not the other font or chat size/width. The UI weight is inherited by ordinary interface/chat text; code/pre, highlighted code (including its inline theme styles), source-view line numbers and diffs use the mono weight. Headings, Markdown bold/inline code inside emphasis, and other explicitly weighted labels keep their original weights; do not blanket-override them with `!important`.
- General no longer exposes the retired Sidebar / File browser placement setting. The file dock is controlled by the workspace; `useFilesPlacement` remains a compatibility fallback for the sidebar's undocked layout.
- General uses centered, equal-width sections with consistent control widths. Its scroll area stays full width; a container query on `.settings-dialog-main` shows two columns only when the settings workspace itself is at least 900px wide, otherwise one. Embedded settings use the workspace top bar's Settings label and render only the left-aligned category tabs underneath, with the existing mobile dropdown below 640px. Do not repeat the Settings title inside the page or push the categories to the far right. Standalone modal settings retain their own title.
- General's Chat section ends with the switch for pi's own `showCacheMissNotices` (#1265), saved in the global settings.json through `/api/cache-miss-notices`, not in the browser: the notices come from the server, and the pi CLI reads the same key. Its note says a project's `.pi/settings.json` can override it. After a save the open chat remounts (`onSessionReloaded`) to show or drop them; see sessions.md, Cache and cost notices.
- ChatInput remeasures an existing draft when the interface font or weight changes. TerminalPanel subscribes in its existing lifetime effect, updates xterm's family and normal weight (its bold stays xterm's default 700, above every base weight) and refits, never restarting the terminal or its SSE stream for a font change.

## Plugins and skills
- `/api/plugins` uses pi's `SettingsManager` + `DefaultPackageManager` for global/project package install, remove, update, enable and disable; disabling writes empty `extensions/skills/prompts/themes` arrays to the package entry. Every POST drops the provider routes' shared runtime, since a package can add or drop a provider ([models.md](models.md), Auth and model config).
- `/api/skills` lists through `DefaultResourceLoader`, so settings paths, package skills and project `.agents/skills` appear as the runtime sees them. The loader takes `noExtensions: true` (`lib/skills-service.ts`, #1226): extensions add skills only through `resources_discover` at `session_start`, which a listing never runs, so importing them added nothing and blocked the event loop on every Skills open, skill click and slash-palette open. Skills an extension discovers never showed there, before or since. Even an empty extension load re-keys the SDK's one-cwd factory cache, so a listing for a folder other than the running sessions' still makes their next start re-import. The detail pane lazily reads a selected skill through `/api/skills/content` and renders its post-frontmatter instructions as Markdown; that route permits only an exact file path returned by the same runtime loader and caps the regular-file read at 1 MiB, rather than becoming a general Markdown-file reader. Toggling a skill edits only the `disable-model-invocation` frontmatter key of its `SKILL.md`, so user formatting survives, and `PATCH /api/skills` edits only `.md` files (its roots also hold `auth.json`, settings and project files). `/api/skills/install` shells through `npx skills add ... --agent pi`; project installs run in the selected cwd.
- Skills detail uses a name/description header, a labelled model-visibility row, a source/version grid with a full wrapping installation path, then the instructions and a compact uninstall action at the bottom. Scoped `.skills-*` styles in `app/settings.css` limit reading width and stack the metadata in narrow panes. Uninstall results are dismissible notices; backup details start collapsed and remain bounded when expanded. `e2e/skills-layout.mjs` isolates APIs and checks desktop, 390/320px phones, the uninstall confirmation/notice, and overflow, with screenshots under `test-results/skills-layout/` (`E2E_LOCALE=zh-CN` for Chinese previews).
- Skills groups combine installed and other skills by project, global and path; the sidebar shows the current cwd and filters loaded skills by name. Group switches are disabled while filtering. The add pane explains that custom skills can be installed with model assistance by sharing a repository link or local path in chat, labels skills.sh as an online search, shows the current CLI installation roots and notes installs in the other scope. The detail shows the full skill path and warns that toggling edits the shared file.
- Skill name collisions use SDK diagnostics and show winner and loser paths. Online search errors expose a short explanation and expandable details. `/api/skills/remove` validates cwd, project trust, loaded path, package and scope, and requires acknowledgement that shared files will become unavailable to other agents. `lib/skill-remove.ts` uninstalls directly without npm/npx: under a per-lock-file `proper-lockfile` lock it rechecks the source and conventional roots, moves the selected skill and any Pi alias to `.pi-web-skill-trash` outside the scanned `skills` directories, saves the original lock and a restore manifest there, then atomically removes only that skill's lock entry. A lock-write failure restores the moved files. Distinct same-name directories, linked parent roots, changed sources and malformed locks are refused before moving files. Individual skill links are moved without deleting their source targets. Independent copies in other agents' directories are kept; shared canonical directories become unavailable, as stated in the confirmation. The route rechecks discovery and the UI refreshes the list, reports success and exposes the backup path. Tests use real temporary global/project directories and SDK discovery, including Windows rollback, aliases, and concurrent removals.
- **Scope changes.** `SkillScopeTransfer` expands under the installation path, previews the opposite scope, and defaults to Move with Copy as an explicit alternative. `/api/skills/transfer` validates origin/JSON, allowed cwd and project trust for both directions; source identity comes from the management loader, never an arbitrary client path. `lib/skill-transfer.ts` rechecks source/target records and directories, refuses conflicts and linked skill trees, copies into staging outside scanned roots, checks content hashes, then commits under both lock-file locks. Source backups and target staging stay on their respective volumes so C:↔D: moves and rollback work. Only the selected lock entries change; ordinary file contents (including local edits and visibility frontmatter) are preserved. CLI project/global revision hashes are not interchangeable: the target stores `piWebVersionHash` for display and has no automatic update check; the form explains this. An in-memory, cwd-bound undo token lasts five minutes; undo refuses changed target files/records or a recreated source, preserves unrelated later installs, and keeps recovery manifests/backups outside skill roots. Do not run sample moves against real installed skills during tests.
- **Shadowed installations.** The default skills catalog remains the SDK's chosen winners. Only `?management=1` on listing/content includes same-name loser paths already reported by SDK collision diagnostics, with `loaded: false`. The settings list marks those copies as inactive and can select the transfer destination even when it loses the name collision. Native removal and scope changes use this management view. They do not change the runtime's precedence rules. `lib/skill-file-paths.ts` owns shared filesystem helpers; transfer and removal import it directly. `e2e/skills-transfer-api.mjs` calls the real listing and preview routes against the existing dev server without applying changes, so a stale/missing route-bundle export is caught in addition to browser fixture tests. Tests cover both scopes, move/copy/undo, conflict and dangling-link refusal, edited-target undo refusal, Windows lock failure rollback, different volumes, and management discovery; browser fixtures exercise transfer/undo at desktop and 390/320px widths.
- **Skill documents.** A local link in the instructions (`MarkdownBody`'s `onNavigateLink`) opens that file in the same Instructions field. `resolveSkillLink()` resolves it from the linking document's folder, as pi resolves a skill's relative paths; `SkillDetail` keeps a stack of the documents opened, the last one shown under one Back button and its relative path. Switching skills remounts `SkillDetail`, emptying the stack. A link or Back brings the field's top, or the `#heading`, into view once the document shows: Back lands at the previous document's top, nothing saves a scroll position. A link to the skill file itself reads it without `document`. The client refuses nothing: an absolute path or a `..` past the folder goes to the route, whose message shows under Back.
- `/api/skills/content`'s optional `document` is a path in the loaded skill's `baseDir` (pi's dirname of the skill file): relative, without `..`, `\`, `:` or NUL, `.md`/`.markdown` by name and by real path, inside the folder after symlinks (`isExistingPathWithinRoots()`), a regular file up to 1 MiB. One stat before the bounded read answers a FIFO or a directory with 400 and a larger file with 413; a missing file is 404, a link out of the folder 403, and no refusal or failed read names a path. Without `document` the route reads the loaded file exactly as before.
- **Group switches.** Each sidebar group of the Skills, Plugins and MCP panels (a skill scope, a package scope, an `mcp.json`; not standalone extensions) has a `ConfigSidebarGroupSwitch` in its heading row, so the list's rows keep the heading's line. As with the Models provider switch, it is on only while every row is: a partial group reads as off beside its `n/m` count and one click completes it. A panel whose group can hold rows its switch never turns on passes its own `checked` (MCP: `mcpGroupSwitchChecked()`), or the switch stays off for good. One request carries the list (`PATCH /api/skills` `filePaths`, `POST /api/plugins` `packages`, `POST /api/mcp` `set-enabled` `servers`) and answers per item, so a refused row does not stop the rest; what was left undone shows under the heading (`ConfigSidebarGroupStatus`). An entry already in the requested state is left alone; enabling keeps an entry's own keys such as `autoload`. `SettingsManager` never throws a failed load or write (`flush()` resolves), so the bulk plugin path reads `drainErrors()`, or an unreadable settings.json would report success. Disabling empties the four resource lists and keeps no filters, so a group switched off leaves an enabled filtered package on (the SDK reports every object entry as `filtered`) and says so; the bulk route refuses it.

## Settings on a phone
- PI-YUN's embedded Settings uses the same phone levels and history as the standalone panel. The workspace entry passes `openAtHome` on phones; explicit section links open that section. Embedded headers omit the repeated title on desktop and keep the centered title and 4px side padding on phones. Source-based tests normalize CRLF before matching function boundaries.
- At ≤640px Settings fills the screen and shows one level at a time (`SettingsPanel`'s `usePhoneSettingsLevel`): the list of sections, a section, then a row's detail. The plain Settings button opens on the sections (`openAtHome`); the sidebar's Models and Skills buttons and a bare `/mcp` open their section. Above 640px the level is always the section, so a desktop window narrowed to a phone's width keeps the section it shows (the e2e's short settings panel check at 320px relies on it). The header is three columns, Back, title, close, the sides equal so the title stays centered and is cut short in its own column; Back is named after the level above and the title is the shown level's name; over a detail that is the active row's label, reported by `ConfigSidebarItem` / `ConfigListAction` after each render (a rename shows at once), never by rows in a hidden, still-mounted section.
- A split view shows one pane through `ConfigDetailNavigationContext` (`data-pane="list" | "detail"`, the phone CSS in `app/settings.css`). A row's or add button's click opens the detail unless its handler called `preventDefault()`: Models' Add provider does, and its picker's choice calls `openDetail()` (`useConfigDetailNavigation()`). Deleting a provider or a model goes back to the list (`closeDetail()`). Outside the provider (no Settings) both panes stack as before. A section's settings row above its list (Models' enabledModels banner, Sub-agents' switch) shows on the list level only (`data-phone-level` on the section host).
- Each level entered pushes a history entry that copies `history.state` (Next's router state) and keeps the URL, so the system Back goes up one level; the panel's Back calls `history.back()` while it has entries, and closing Settings drops them (`history.go(-n)`). Desktops never push.
- A level change animates with the Web Animations API (`animatePhoneLevelChange`, from a layout effect so the new level never shows in place first): going in, the main area slides in from the right with a fading edge shadow; going back, from 30% left, fading up; the header's Back and title fade in beside it. Only the new level moves (the old one is gone at once) and `.settings-dialog-main` clips it. Nothing moves under `prefers-reduced-motion`.

## Shared blocks
- Settings distinguish explicit model-draft saves from automatically saved switches. Skill visibility shows saving/saved feedback only after its PATCH succeeds; MCP and skills explain that switch changes save automatically. These messages do not promise a running session has reloaded its resources.
- Panels are built from the shared blocks in `components/SettingsUi.tsx` (`ConfigScopeTag`, `ConfigScopeSwitch`, `ConfigSaveTarget`, `ConfigAddSourceHeading`, `ConfigAddSourcePanel`, `ConfigDetailGrid`, `ConfigFooterStatus`, `ConfigTrustNotice`), `itemsToSwitch()` in `components/settings-ui-helpers.ts`, and `lib/display-path.ts`; a new settings section reuses them instead of copying a panel. `SettingsUi.tsx` takes every word as a prop and holds no state, so it renders outside the i18n provider; panels pass `t()` strings.
- **Every add pane chooses global or project in one place:** a `ConfigSaveTarget` (scope switch aria-labelled `config.saveTo`, plus the path that choice writes to) first under the pane's title, where a detail pane shows its `ConfigScopeTag` and path. Skills, Plugins and MCP get it through `ConfigAddSourceHeading` (title, the catalog links at its right, then the save target); Sub-agents put it in the detail header in place of the tag while creating. The submit button stays where its flow needs it (Install under the source box or on each skill result, Save in the footer, Add at the end of the MCP form), with why it waits beside it, not under the save target. The path is shown whole, never cut short: it wraps after a separator (`<wbr>`), then anywhere. Sub-agents offer both scopes whatever the folder's trust: profiles are not project resources that wait for it.
- **Why a control is unavailable is visible text** — a scope switch's `disabledReason` (under the switch's whole line, so controls passed as its `children` stay level with it), the note under a detail header, a footer summary that opens its diagnostics — never only a `title` tooltip, which a touch screen cannot show.
- `ConfigTrustNotice` shows its button only when given `onTrust`; Settings › MCP passes AppShell's trust dialog through `SettingsPanel` (see **Trust from Settings** in [mcp-settings.md](mcp-settings.md)). Skills takes `onOpenTrustDialog` through SettingsPanel as `onTrustProject` and offers the same Trust action while the page status says `requiresTrust && !trusted`; the existing AppShell dialog still confirms the decision. Skills and Plugins take the page's `trust` and reload in place after a decision. Plugins has no Trust button.


## Workbench settings entry points
- `AppUpdateButton` is the rail's first bottom utility, above the pet and Settings (and a labelled entry in the mobile drawer). It shows the installed pi-yun and bundled pi versions in a `SidebarMenu` dialog/sheet, uses `/api/app-update` for the fork's own npm release, and turns blue only when its latest stable version exceeds the installed app version. A failed check stays unknown or retains a previously known update; it never claims the app is current. Foreground checks respect the endpoint's 12-hour cache, abort on unmount, and can be retried from the dialog. The release link is derived from a validated version and appears only for an available app update. The global npm update command and deployment/restart instructions are always visible, including when the app is current or a check fails. `e2e/app-update.mjs` covers current/older/newer, failure/retry/malformed responses, focus/Escape, placement, dark mode and mobile.
- The desktop Settings header replaces the passive session name with a quiet Back to conversation button when a session or composer exists. Its tooltip names the session, and it uses `navigateWorkspace("chat")`, preserving the mounted transcript, scroll and draft. Keep the Settings label as a separate context button so focused file tabs can still switch back to Settings; never nest the return button in that button. Mobile retains its existing Settings close/navigation controls.
- AppShell has its primary Settings entry in the 52px rail at the far left on desktop (`app/navigation-rail.css`), available even when the session sidebar is collapsed. Models, Skills and the other categories remain in SettingsPanel's navigation; do not duplicate them as rail shortcuts. The entry opens the last available settings section, keeps its tooltip and accessible name, and stays active for any open settings section. Project requirements are checked inside SettingsPanel.
- Phones render the same navigation once as a labelled row at the bottom of the session drawer; do not add a second set of interactive buttons. Desktop panel width limits reserve the rail's 52px.
- Desktop rail entries are fixed workspace destinations, plus a separate companion visibility toggle that never navigates away from the current view. Generate title stays beside the conversation title. Mobile session actions remain in the chat header/overflow and enter the same embedded views.

- The PI-YUN application dropdown links to the same embedded Settings page through the shell setter; it adds no category or persistence of its own.

- AppShell mounts `SettingsPanel embedded` inside the central workspace, with `role="region"`, no modal backdrop/geometry and the existing section tabs. The default nonembedded component remains available to other callers. Escape and focus restoration still protect a running conversation, and nested trust/sign-in dialogs retain their stacking behavior. Leaving Settings through any rail entry refreshes the model catalogue, just as Close does. The project/session sidebar remains interactive.
